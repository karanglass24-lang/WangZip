# WangZip 설계 문서

이 문서는 구현에 들어가기 전 수행한 설계 검토 결과와, 실제 구현에서 내린 결정을 기록합니다.
"왜 이렇게 만들었는지"를 남겨 이후 기여자가 같은 함정을 반복하지 않도록 하는 것이 목적입니다.

---

## 1. 목표와 제약

| 항목 | 결정 |
|---|---|
| 대상 | Windows 11 우선 (Windows 10은 최선 노력) |
| 라이선스 | GPL-3.0 — 광고·번들웨어를 넣은 폐쇄소스 포크 방지 |

## 2. 초기 설계에서 정정한 사실

설계 검토 과정에서 아래 4가지를 바로잡았습니다. 초기 안대로 갔다면 일정과 라이선스 양쪽에서
큰 손실이 발생했을 항목입니다.

| 초기 가정 | 실제 | 구현에 미친 영향 |
|---|---|---|
| 7-Zip SDK는 LGPL이라 링크 불가 | **LZMA SDK는 퍼블릭 도메인**. LGPL은 7-Zip 응용프로그램에만 해당 | 향후 7z 쓰기를 SDK 링크로 구현 가능. 다만 v0.1은 SharpCompress 읽기만 |
| 7z.exe 호출로 진행률/취소 처리 | 7z CLI에는 기계 판독용 진행률이 없음. 퍼센트 파싱은 취약 | v0.1에서 7z 쓰기를 과감히 제외 |
| Windows 10/11 동시 지원 | Windows 10 지원 종료 | Windows 11 기준으로 검증 범위 축소 |
| .NET 8 WPF | .NET 8 LTS 종료 임박 | **.NET 10 LTS**로 시작 |

추가로 확인한 제약:

- Windows 11의 새 우클릭 메뉴(`IExplorerCommand` + sparse package)는 **신뢰된 코드 서명이 없으면 설치 불가**.
  셸 확장은 서명 예산(SignPath OSS 무료 프로그램 등) 확보 후 v0.3에서 진행합니다.
- unRAR은 OSI 정의의 오픈소스가 아니므로 저장소에 포함하지 않습니다.

## 3. 아키텍처

v0.1은 **단일 C# 스택**을 선택했습니다. 1인 개발에서 C++ 엔진 + C# UI + C++ 셸 확장의
3개 툴체인은 빌드·디버깅 비용이 기능 개발 시간을 잠식하기 때문입니다.

```text
WangZip.App (WPF)
   │  in-process 호출
   ▼
WangZip.Core
   ├─ Zip/            ZIP 직접 파서 + 추출/생성
   ├─ Safety/         경로 안전, CRC
   └─ SharpCompress   7z/TAR/GZ/BZ2/XZ/RAR 읽기
   │
WangZip.Cli           동일 엔진의 CLI (자동화·테스트·장애 격리 수단)
```

장기적으로 성능이 병목이 되면 `WangZip.Core`의 ZIP 경로를 C++/libarchive 백엔드로 교체할 수 있도록
`IArchiveSource` 인터페이스로 분리해 두었습니다. UI는 엔진 구현을 알지 못합니다.

### 왜 ZIP만 직접 구현했나

- 파일명 **원본 바이트**를 얻어야 한글 인코딩 판별이 가능합니다. `System.IO.Compression`은
  해석된 문자열만 제공합니다.
- 항목별 CRC 검증, 정확한 진행률, 취소, 원자적 쓰기를 직접 제어할 수 있습니다.
- ZIP은 명세가 공개되어 있고 구현 범위가 명확합니다.

7z/TAR/RAR은 포맷 복잡도 대비 읽기 수요가 커서 SharpCompress(MIT)에 위임했습니다.

한 가지 예외가 있습니다. `.tar.gz` / `.tar.bz2` / `.tar.xz`는 `ArchiveFactory`로 열리지 않습니다
(압축 스트림 안에 TAR이 있는 중첩 구조라서). 이 형식만 `ReaderFactory.OpenReader` 기반의
전진 읽기 백엔드(`ReaderArchiveSource`)로 처리합니다. TAR은 항목별 압축 크기가 없으므로
목록의 "압축 크기"는 원본 크기와 같게 표시됩니다.

## 4. 한글 파일명 판별

ZIP의 파일명은 "CP437 또는 UTF-8"로 규정되어 있지만, 실제 파일은 CP949/EUC-KR/Shift-JIS 등
다양합니다. 판별은 다음 우선순위를 따릅니다.

1. 유니코드 경로 추가 필드 `0x7075` (CRC가 원본 이름과 일치할 때만)
2. 일반 목적 플래그 bit 11
3. ASCII
4. 엄격 UTF-8 + 한글 포함
5. 엄격 CP949 + 한글 포함
6. 엄격 UTF-8 → 7. 엄격 CP949 → 8. CP437

핵심 아이디어: CP949로 인코딩된 한글 바이트는 우연히 **유효한 UTF-8**이 되는 경우가 많지만
(예: `C7 D1 B1 DB`), 그 결과에는 한글이 없습니다. 따라서 "UTF-8로 해석했을 때 한글이 나오는가"를
결정적 신호로 사용합니다. 반대 방향(UTF-8 한글을 CP949로 오해)은 드물지만 가능하므로
UI에서 수동 전환이 가능해야 합니다.

추가 처리:

- **NFC 정규화**: macOS ZIP의 NFD 자모 분리 문제 해결
- **혼합 인코딩 허용**: 항목별 판별 후 아카이브 전체 통계를 상태바에 표시

## 5. 안전 계층

압축 파일은 공격자 제어 입력으로 취급합니다. 추출 경로는 반드시 `PathGuard`를 통과합니다.

| 위협 | 처리 |
|---|---|
| zip-slip (`../`) | 정규화 후 대상 루트 이탈 시 예외 |
| 절대 경로 / 드라이브 문자 | 루트 기준 상대 경로로 강제 |
| Windows 예약 장치명 | `_` 접두사 |
| ADS (`file:stream`) | `:` 치환 |
| 대소문자 충돌 | `(2)` 접미사 자동 부여 |
| 후행 점/공백 | 제거 |
| 긴 경로 | `\\?\` 확장 경로 |
| 심볼릭 링크 | 기본 건너뜀 |
| 손상 데이터 | 파일 크기 + CRC 검증, 불일치 시 예외 |
| 부분 추출 잔여물 | 임시 파일 → 성공 시 rename |
| 디스크 부족 | 사전 여유 공간 확인 |
